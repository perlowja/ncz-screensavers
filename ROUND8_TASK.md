## Why glmark2, not xscreensaver, for this round
glmark2 (github.com/glmark2/glmark2, GPL-3.0) is a GLES2/GLES3-NATIVE benchmark — its scenes are already shader-based (GLSL ES, VBOs), not legacy fixed-function GL. That means NO translation layer (no GL4ES) is needed to port them — same category of work as our existing rotating-triangle test effect, just real, polished, screensaver-worthy visual algorithms instead of a placeholder. glmark2-es2-drm and glmark2-es2-wayland are already packaged and known-working on THIS exact board family (cixmini/Sky1) — real proof the shader techniques run fine on this GPU.

## The actual glmark2 scenes to look at (fetch source from github.com/glmark2/glmark2, path src/, on forky where you have real internet + file access — do NOT try to paste large source blocks back to the coordinator in chat; work with the files locally)
- `scene-pulsar.cpp` — a particle system (many small quads/points pulsing/orbiting). Classic screensaver material, GLES2-friendly (point sprites or instanced quads), good structural complexity without being huge.
- `scene-ideas.cpp` (+ the `scene-ideas/` subdirectory) — a Bezier-curve-driven wave/ribbon morphing effect. Visually distinctive.
- `scene-jellyfish.cpp` (+ `scene-jellyfish.h`) — animated translucent jellyfish with tentacle physics; more complex but very screensaver-appropriate if time allows.
Pick AT LEAST 2 of these 3 (pulsar is probably the best first pick — self-contained, clearly particle-based, moderate complexity). If jellyfish turns out too complex for one round, do pulsar + ideas and note jellyfish for a future round.

## What "port" means here (same discipline as the round-1 spec's effect API)
This is NOT copy-pasting glmark2's C++ into our C tree. It won't even compile (different language, different windowing/GL-loading infra, different build system). Read each scene's actual algorithm — what geometry it generates, what its vertex/fragment shaders do, what per-frame state it updates (particle positions/velocities, Bezier control points, phase/time uniforms) — and REIMPLEMENT that algorithm as a new effect in THIS codebase's style and language (C11, GLES2, matching the existing `triangle_init/reshape/draw/free` pattern from src/wl-screenhack.c). Use glmark2's actual GLSL shader source as a strong reference/starting point for the shaders specifically (GLSL translates far more directly than the C++ scene-management code around it) — but the C-side state management, VBO setup, and effect lifecycle should follow THIS project's existing conventions, not glmark2's C++ class structure.

Attribution: at the top of each new effect source file, a comment noting it's adapted from glmark2's `scene-<name>.cpp` (github.com/glmark2/glmark2, GPL-3.0), citing the original project. This is the same attribution discipline round 7 already uses for xscreensaver-derived work.

## Reference note for later work (do not implement this round — just be aware)
glmark2's `native-state-drm.cpp`/`native-state-gbm.cpp` implement a compositor-BYPASS fullscreen backend: direct DRM/KMS mode discovery (libdrm connector/CRTC/mode enumeration), a GBM buffer-backed surface, and EGL via the GBM platform — no Wayland/X11 compositor involved at all. That's a useful reference pattern for a POSSIBLE future "no compositor available" fallback mode for ncz-screensavers (e.g. running as a bare login-screen-adjacent fallback), but it's out of scope for this round — this round's target is the existing wlr-layer-shell/Wayland path from rounds 1-6, which already works. Just don't be surprised if a future round asks for a DRM-direct backend as an alternative to the Wayland one; the architecture should stay open to that (keep windowing/surface-acquisition code separated from effect/rendering code, which rounds 1-6 mostly already did).

Build cleanliness: -Wall -Wextra, zero warnings, zero errors, same bar as prior rounds.
