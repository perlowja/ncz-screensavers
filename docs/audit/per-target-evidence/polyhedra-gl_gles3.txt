--- summary ---
VERIFIED: native GLES3 port. No libgl4es.so. No libGL.so.1. No libglu
tessellator link. Vendored hack source linked in (polyhedra_xscreensaver
_function_table present).

KNOWN VISUAL TRADEOFF (documented for operator review, not hidden):
The -DHAVE_JWZGLES flag flips the polyhedra-gl source's
#ifndef HAVE_JWZGLES / #define HAVE_TESS gate (line 51-53) to its
#else branch (the flat-face fallback at lines 406-417). The
tessellator path is responsible for triangulating nonconvex faces.
The fallback emits glBegin(GL_LINE_LOOP / GL_TRIANGLES / GL_QUADS /
GL_POLYGON) per face — geometrically correct for convex faces
(cube, octahedron, dodecahedron, icosahedron, etc.), but produces
incorrect winding / missing triangulation for nonconvex face
selections. The source comment at line 322 cites the
"pentagrammic concave deltohedron" as the case the tessellator
exists to handle (the 5-pointed-star nonconvex face). The
polyhedra themselves are constructed dynamically by kaleido() over
a Wythoff table in polyhedra.c; the only entry in that table whose
faces are guaranteed nonconvex is the pentagram-faced one
("X005|2" in Wythoff notation, the small stellated dodecahedron
family). User-selectable via the `-which` resource; if a user
selects that value (or any other nonconvex-face entry the Wythoff
generator emits), the face renders as a self-intersecting flat
polygon instead of the triangulated outline the tessellator would
produce. Convex-face selections are visually unchanged.

This is a documented, bounded tradeoff the operator chose to accept
per the Phase 4+ final-6 plan rather than port the full GLU
tessellator to GLES3 (which is the architectural blocker also
shared by dnalogo; both dnalogo and the GLU tessellator remain
deferred per the directive's bounds).

Visual verification on real hardware: BLOCKED (same as every prior
port in this project — O6N labwc headless backend, no wl_output).
EGL/GLES3 context pipeline confirmed end-to-end via the strace
library-load sequence above.
