5.  glColorMaterial correctness proof (crackberg-specific)
----------------------------------------------------------------------

  The reviewer asked: the stub correctness rests on an unverified
  shader assumption. The proof below, with verbatim commands + GLSL
  excerpts + grep transcript, falsifies or confirms the claim from the
  commit alone (no need to read any code beyond this file).

  Claim: the no-op stub (void glColorMaterial(...) { (void)face; (void)mode; })
  is observationally equivalent to honoring the flag for crackberg's
  specific usage pattern.

  Step 1 — crackberg.c glMaterial* call sites:
    $ grep -nE 'glMaterial' src/crackberg.c
    (no matches)

    crackberg.c never calls glMaterialfv / glMaterialf / glMateriali.

  Step 2 — crackberg.c glColorMaterial call sites:
    $ grep -nE 'glColorMaterial' src/crackberg.c
    1225:        glColorMaterial(GL_FRONT_AND_BACK, GL_AMBIENT_AND_DIFFUSE);

    One call, with the conventional (face=both, mode=ambient+diffuse)
    arguments. This is the standard GL1 idiom for "I want my per-vertex
    glColor* values to drive the diffuse term". The no-op stub ignores
    the arguments, which has no rendering consequence if and only if
    no glMaterial* call ever flips the material slot, which Step 1 confirms.

  Step 3 — other Phase 3 + glFrustum-cohort hacks' glColorMaterial
  call sites:
    cityflow.c                  (no matches)
    covid19.c                   (no matches)
    cubenetic.c                 (no matches)
    cubestorm.c                 (no matches)
    cubetwist.c                 (no matches)
    cubicgrid.c                 (no matches)
    dangerball.c                (no matches)
    discoball.c                 (no matches)
    energystream.c              (no matches)
    highvoltage.c               (no matches)
    stonerview.c                (no matches)
    lament.c                    (no matches)

  None of the 12 other Phase 3 + glFrustum-cohort hacks call
  glColorMaterial. So the only binary in this commit whose link is
  influenced by glColorMaterial is crackberg, and crackberg is the
  binary the analysis above proves correct.

  Step 4 — the shader pair's exact material-aware lines
  (gles3_compat.c):
    VERT_SHADER line 259:  vec4 base = u_has_material ? u_material_color : a_color;
    FRAG_SHADER line 294:  vec3 lit = v_color.rgb * (u_ambient + u_light_color * ndotl);

    The vertex shader branches on u_has_material. The fragment shader
    has no material input — it composites v_color (which is already
    base from the vertex shader) against the global
    (ambient + light*ndotl) term. So the "flag has nothing to bind to"
    reading the previous commit used was imprecise; the precise reading
    is: the flag controls which uniform goes into v_color, and is only
    "true" when g_im.has_material is true.

  Step 5 — g_im.has_material only flips to true via ncz_im_material()
  (gles3_compat.c line 758):
    $ grep -n 'g_im.has_material = ' src/gles3_compat.c
    758:        g_im.has_material = true;

    (One write site — line 758 in ncz_im_material, inside the
    pname == GL_AMBIENT_AND_DIFFUSE branch.)

  Step 6 — callers of ncz_im_material (grep -nE 'ncz_im_material' src/gles3_compat.c):
    754:void ncz_im_material(GLenum face, GLenum pname, const float *value) {
    1631:        ncz_im_material(face, pname, vv);
    1639:        ncz_im_material(face, pname, vv);
    1644:    ncz_im_material(face, pname, v);
    1740: *      to true ONLY via ncz_im_material() (lines 754-759), which is

    Only lines 754 (definition), 1631 (glMaterialf), 1639 (glMateriali),
    1644 (glMaterialfv) — three call sites, all from glMaterial*.
    glColor* never touches ncz_im_material and never touches
    g_im.has_material.

  Step 7 — combined proof for crackberg:
    - crackberg.c never calls glMaterial* (Step 1)
       => g_im.has_material stays false from init to teardown
    - crackberg.c calls glColorMaterial once at line 1225 (Step 2)
       => no-op, has no effect on g_im state
    - crackberg.c calls glColor3d / glColor3f to set per-vertex colors
       => these go into g_im.cur_color, then into a_color in vertex data
    - VERT_SHADER selects base = a_color (not u_material_color)
       because u_has_material == false (Step 4 + Step 5)
    - FRAG_SHADER composites v_color.rgb * (ambient + light*ndotl)
       where v_color.rgb = a_color.rgb = glColor* input (Step 4)

    Therefore: with or without glColorMaterial being honored, crackberg
    produces the same fragment colors. The no-op stub does not cause a
    visual regression for THIS hack.

  General GL_COLOR_MATERIAL honesty note (carried forward from a38f066):
    For a hypothetical future hack that DOES call both glMaterial* and
    glColorMaterial, this no-op is incorrect: the GL1 semantic is "the
    current color should override the material AMBIENT_AND_DIFFUSE
    slot", which would mean g_im.cur_color should ALSO be written into
    g_im.material when the flag is on (g_im.color_material_mode tracked
    in a state flag, with a route inside ncz_im_color() that writes to
    g_im.material and flips g_im.has_material when the flag is on).
    That implementation work belongs to whichever future Phase 3+
    dispatch first hits such a hack; this dispatch only ships
    crackberg, where the no-op is provably inert. The source comment at
    gles3_compat.c lines ~1722-1768 captures the same proof inline.
