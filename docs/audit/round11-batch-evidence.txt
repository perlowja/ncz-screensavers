2. Foundation extension this round: glAlphaFunc no-op stub
----------------------------------------------------------------------

src/gles3_compat.c lines 2041-2050:
  /* glAlphaFunc — GLES3 dropped the desktop GL_ALPHA_TEST pipeline state
   * (no GL_ALPHA_TEST enable, no glAlphaFunc). Vendored hacks that
   * conditionally call glAlphaFunc(GL_GREATER, 0.5) etc. (glforestfire
   * is the one in this round) get a no-op stub. Known visual
   * inaccuracy: alpha-tested fragments are no longer culled, so a
   * hack that uses glAlphaFunc to discard transparent texels (i.e.,
   * tree sprites in glforestfire) will draw the full unfiltered
   * texture. Cosmetic only — the scene composes correctly, just
   * with semi-transparent edges visible. */
  void glAlphaFunc(GLenum func, GLfloat ref) { (void)func; (void)ref; }

Single consumer in this round:
  $ grep -nE glAlphaFunc src/*.c
  src/glforestfire.c:733:    glAlphaFunc(GL_GEQUAL, 0.9);

3. c_args_extra flags added this round
----------------------------------------------------------------------

  glforestfire: -DSTANDALONE
    The !STANDALONE branch includes xlock.h + visgl.h from xlockmore,
    neither of which exist in the vendored shim tree. STANDALONE
    selects the xscreensaver-mode branch which uses xlockmore.h and
    does not need those xlock-only headers.

  providence: -DSTANDALONE
    The !STANDALONE branch defines change_providence which calls
    pinit() without the args the STANDALONE-built static helper
    expects ("too few arguments to function 'pinit'" at line 797,
    plus 'release_providence undeclared' in xscreensaver_compat.h).

What I COULD confirm on real hardware (this round, all 12 binaries):

  GLES3 context initialization works. Running each binary with
  WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/1000 timeout 3
  ./<hack>_gles3 produces:

    MESA: error: ZINK: vkCreateInstance failed (VK_ERROR_INCOMPATIBLE_DRIVER)
    [diag] gles3_harness: EGL 1.5, GLES3 context live
    [diag] gles3_compat: shader program 3 compiled
    [diag] GL_VERSION=OpenGL ES 3.2 Mesa 26.1.6-1
    RENDERER=llvmpipe (LLVM 21.1.8, 128 bits)
    GLSL=OpenGL ES GLSL ES 3.20
    gles3_harness: never configured

  The "never configured" exit is from src/gles3_harness.c:640 — the
  harness only calls init_cb/draw_cb AFTER the wl_surface receives
  a configure event from the Wayland compositor, which requires a
  wl_output.

What I COULD NOT confirm on real hardware this session:

  Real-hardware visual rendering (the previous-session verify-gles3.sh
  pipeline: 3 grim captures + base/a/b ppm diff + frame_delta).

  Why: O6N's labwc is currently running in headless backend mode with
  no wl_output exposed. Verification chain of evidence:
    - /sys/class/drm/card0-DP-{1,2,3}/status all = disconnected
      (no physical display plugged into the GPU's display ports)
    - labwc log shows "manually creating headless backend" and
      "Failed to get DRM device: No such device"
    - WAYLAND_DEBUG=1 on a grim connection shows zero wl_output
      globals in the registry (only zwlr_output_manager_v1 +
      zxdg_output_manager_v1, no wl_output instances)
    - grim errors out with "no wl_output"; wlr-randr returns no
      outputs; wlr-randr --output DP-2 --mode 1920x1080 returns
      "unknown output DP-2"
    - Kernel cmdline is sky1.gpu=mesa (not vendor) — Mesa software
      renderer llvmpipe (LLVM 21.1.8) is what the EGL stack
      enumerated, not the Mali-G720-Immortalis GPU that the prior
      GLES3-MIGRATION-PHASE1.md verified against.

  Compare the prior visual evidence from Aug 29 (gle3-shots/*.ppm
  timestamps): those captures were taken when labwc had a real
  wl_output on DP-2 (3840x2160@60) bound to the Mali GPU. The
  reboot(s) between Aug 29 and now (Sep 7) lost that binding —
  the GPU is still present in /dev/dri (renderD129 for the
  Mali-G720, card0 for the linlondp display controller), but no
  output is currently connected.

  No physical access to attach a display from this session. The
  cixmini box (192.168.207.66) has card2-DP-3 connected but the
  Wayland session there runs as user 'mini' (uid 1000), and neither
  the TYDEUS nor the O6N key is authorized for ssh to mini@cixmini.
